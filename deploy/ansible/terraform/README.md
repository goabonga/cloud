# Provision infra with Terraform

Four independent examples, each its own root module with its own state:

| Directory | Shows | Resources |
| --- | --- | --- |
| [`compute/`](compute/main.tf) | A namespaced container workload | `infra_compute` |
| [`faas/`](faas/main.tf) | A FaaS function with a warm pool | `infra_function` |
| [`vm/`](vm/main.tf) | A single real VM under infra-hypervisor | `infra_microvm` |
| [`k8s/`](k8s/main.tf) | A 3-node kubeadm cluster, VM per node | `infra_microvm` |

Run `terraform apply` from inside one of them, against the deployed control
plane. Applying one never touches another: each has its own VPC, subnet and
state.

The control VM already has Terraform, the provider and all four workspaces
set up (`ssh ubuntu@192.168.122.10`, `infra-login`, `cd ~/infra-demo/compute`,
`terraform apply`; see [../README.md](../README.md)). This page covers
running them from the libvirt host instead.

The provider is not published to a registry yet, so Terraform uses a local
build via `dev_overrides`.

## Prerequisites

- The stack is deployed with `ansible-playbook site.yml` (etcd, control plane,
  IdP, agents registered as nodes).
- The provider binary is built: from the repository root, `make build-provider`
  (produces `build/terraform-provider-infra`).

## One-time setup

1. Point Terraform at the local provider. Copy the example and edit the path:

   ```bash
   cp terraform.tfrc.example terraform.tfrc
   # edit terraform.tfrc: set the dev_overrides path to <repo>/build
   export TF_CLI_CONFIG_FILE="$PWD/terraform.tfrc"
   ```

   `TF_CLI_CONFIG_FILE` is a CLI-wide setting, not tied to a directory: once
   exported, it applies no matter which example directory below you `cd` into.

2. Get an API token (a JWT from the IdP) into the environment:

   ```bash
   export GOA_API_TOKEN="$(./get-token.sh)"
   ```

   `get-token.sh` reads the Terraform client secret from
   `../.credentials/terraform-client.secret` (generated by the playbook).

## Apply an example

`cd` into one of the four directories above, then:

```bash
terraform init
terraform plan
terraform apply
```

`dev_overrides` only covers the `infra` provider; `vm/` and `k8s/` also use
`tls` (a public-registry provider, to generate their SSH key pair), so `init`
still has to run once in each to fetch it.

Override the endpoint if your control host differs:

```bash
terraform apply -var 'endpoint=http://<control-ip>:8080'
```

### `compute/`: a namespaced container

One VPC, one private subnet, a security group opening port 80, and a single
`infra_compute` instance running nginx - the minimal path from zero to a
scheduled, reachable workload.

```bash
terraform apply
terraform output web_ip
terraform output web_phase   # Ready once nginx is scheduled and healthy
```

Reach it from an agent host's own VRF, the same way the VPC's traffic reaches
the rest of the network (there is no load balancer or public address here):

```bash
ssh ubuntu@<agent-ip> 'sudo ip vrf exec "$(ip -br link show type vrf | cut -d" " -f1)" curl -s http://<web_ip>/'
```

### `faas/`: a FaaS function

One VPC, one private subnet, a security group, and a single `infra_function`
with a small warm pool (`min_warm = 1`). Realized as ordinary compute
instances a controller creates and retires to the warm-pool policy - see
[`internal/domain/resource/function.go`](../../../internal/domain/resource/function.go)
- invoked synchronously over HTTP through infra-api, not through Terraform:

```bash
terraform apply
terraform output function_id
terraform output function_phase        # Ready once the warm pool has an instance up
terraform output function_warm_count

ssh ubuntu@192.168.122.10 'infra-login && curl -s -X POST "$GOA_API_URL/api/v1/function/<function_id>/invoke" -H "Authorization: Bearer $GOA_API_TOKEN"'
```

### `vm/`: a single micro-VM

One VPC, one private subnet, a security group opening port 22, and a single
`infra_microvm` - a real VM under infra-hypervisor (see
[../../../docs/architecture/realization.md](../../../docs/architecture/realization.md#microvms)),
as opposed to the namespaced container `compute/` runs. A `tls_private_key`
resource generates the SSH key pair; no `user_data` is given, so the agent
writes a minimal cloud-config from the hostname and that key itself (`k8s/`
below shows the alternative: a full `"#!"` script, overriding the generated
one entirely).

```bash
terraform apply
terraform output vm_ip
terraform output vm_phase    # Ready once infra-hypervisor has booted it
terraform output -raw ssh_private_key > vm-demo.key && chmod 600 vm-demo.key
ssh -i vm-demo.key ubuntu@<vm_ip>
```

### `k8s/`: a 3-node kubeadm cluster

`infra_microvm` boots a real VM under infra-hypervisor for each node (one
control plane, two workers) instead of a namespaced container - see
[../../../docs/architecture/realization.md](../../../docs/architecture/realization.md#microvms).
infra-hypervisor ships inside the `infra-agent` package the agent role
already installs; the agent hosts just need a raw base image, staged by
the `microvm` Ansible role (part of `site.yml`); nothing extra to build.
Each node gets 2 vCPUs and 2048MiB of RAM, enough to clear kubeadm's own
preflight checks (1700MiB minimum) - see `vm/` above for a plain VM at a
fraction of that weight.

A `tls_private_key` resource generates the SSH key pair used to reach every
node - nothing to pass in on the command line, and the private half never
touches disk outside Terraform's own state. Create the control plane on its
own first - a worker's `kubeadm join` needs its address, which the agent only
assigns once it reconciles the resource, not within the same apply:

```bash
terraform apply -target=infra_microvm.k8s_control_plane
```

Wait for it to reach `Ready` (`terraform state show infra_microvm.k8s_control_plane`
or the dashboard) and for kubeadm to come up, then apply the rest:

```bash
terraform apply
```

```bash
terraform output k8s_control_plane_ip
terraform output k8s_worker_ips
terraform output -raw k8s_ssh_private_key > k8s-demo.key && chmod 600 k8s-demo.key
ssh -i k8s-demo.key ubuntu@<k8s_control_plane_ip> kubectl get nodes
```

A worker's join uses a fixed token (`local.k8s_join_token` in `k8s/main.tf`)
and skips verifying the control plane's CA hash
(`--discovery-token-unsafe-skip-ca-verification`): neither the real token nor
the hash `kubeadm init` generates is knowable before it has actually run,
which a single apply cannot wait for. Fine inside this lab's own private
subnet; not a pattern for a real cluster.

## Tear down

From inside the example's own directory:

```bash
terraform destroy
```
